
# Spotify Analytics — MongoDB

## Опис проєкту

У цій домашній роботі я працював із датасетом Spotify Tracks Dataset, який містить 114 000 музичних треків.

Мета роботи — завантажити дані в MongoDB Atlas, перетворити їх у документоорієнтовану структуру, виконати запити до даних та перевірити роботу індексів.

**Використані технології:**
- MongoDB Atlas
- MongoDB Shell (mongosh)
- Python
- PyMongo
- Pandas
- JavaScript (MongoDB Query Language)

**Датасет:** [Spotify Tracks Dataset на Kaggle](https://www.kaggle.com/datasets/maharshipandya/-spotify-tracks-dataset)

## 2. Частина 1. Завантаження даних та проєктування схеми

### 2.1. Завантаження сирих даних

Для завантаження використав Python-скрипт `scripts/01_load_data.py`.

Скрипт читає CSV-файл через Pandas, приводить числові та булеві значення до потрібних типів, видаляє записи без назви треку або виконавця та завантажує документи в MongoDB партіями по 1000 записів.

**Результати завантаження:**

- База даних: `spotify`
- Колекція: `tracks_raw`
- Кількість записів у CSV: 114 000
- Завантажено документів: **113 999**
- Відфільтровано записів: 1

### 2.2. Трансформація схеми

Для трансформації використав `scripts/02_transform.js` з Aggregation Pipeline.

Під час трансформації:

1. За допомогою `$project` вибрав необхідні поля.
2. Через `$split` і `$map` перетворив рядок виконавців на масив.
3. Створив вкладений об'єкт `audio_features`.
4. Додав поле `duration_sec` з тривалістю у секундах.
5. Додав поле `popularity_tier` залежно від популярності треку.
6. Видалив зайві плоскі поля через `$unset`.
7. За допомогою `$out` записав результат у колекцію `tracks`.

Поле `popularity_tier` має три можливі значення:

- `high` — популярність від 70;
- `medium` — популярність від 40 до 69;
- `low` — популярність менше 40.

**Результат:** створено колекцію `tracks`, яка містить 113 999 документів.

### 2.4. Теоретичні питання

#### 1. Чому аудіохарактеристики винесені в окремий об'єкт `audio_features`, а не зберігаються плоско? Коли таке вкладення вигідне, а коли створює проблеми?

Аудіохарактеристики винесені в окремий об'єкт `audio_features`, тому що всі вони описують властивості музичного треку. На мою думку, так структура документа стає більш логічною та зрозумілою, оскільки пов'язані між собою дані зберігаються разом.

Це зручно, коли потрібно працювати з аудіохарактеристиками, наприклад шукати треки за рівнем енергії або темпом. До потрібного поля можна звернутися через `audio_features.energy` або `audio_features.tempo`.

Але така структура має і недоліки. Запити до вкладених полів можуть бути трохи складнішими, а при оновленні всього об'єкта можна випадково перезаписати інші характеристики. Також плоска структура іноді зручніша для експорту даних у CSV або роботи з таблицями.

Тому вкладені об'єкти краще використовувати, коли декілька полів логічно пов'язані між собою та часто використовуються разом.

#### 2. Чому виконавці зберігаються як масив, а не як рядок? Які запити стають простішими?

Виконавці зберігаються як масив, тому що один трек може виконуватися кількома артистами. Наприклад, замість рядка `"Drake; Future"` ми отримуємо масив `["Drake", "Future"]`.

Такий формат значно зручніший для пошуку та аналізу даних. Наприклад, можна знайти всі треки певного виконавця, навіть якщо він записав пісню спільно з іншими артистами.

Також можна використовувати оператор `$all` для пошуку треків із кількома конкретними виконавцями, `$size` для перевірки кількості артистів та `$unwind` для аналізу кожного виконавця окремо.

Якби виконавці залишалися звичайним рядком, для таких операцій довелося б додатково розділяти текст або використовувати складніші умови пошуку.

Тому масив у цьому випадку краще підходить для зберігання даних і спрощує подальші запити в MongoDB.

## 3. Частина 2. Запити до даних

Усі запити цієї частини знаходяться у файлі `queries/part2_queries.js`.

### 3.1. Завдання 1. Треки для вечірки

Потрібно знайти треки з `danceability > 0.7`, `energy > 0.7` та тривалістю від 180 000 до 300 000 мс.

Для фільтрації використав `find()` та оператори `$gt`, `$gte` і `$lte`.

```javascript
db.tracks.find({
  "audio_features.danceability": { $gt: 0.7 },
  "audio_features.energy": { $gt: 0.7 },
  duration_ms: { $gte: 180000, $lte: 300000 }
});
```

**Результат:** знайдено **7 311 треків**.

Наприклад, трек *Hold On – Remix* має `danceability = 0.755`, `energy = 0.78` та тривалість 188 133 мс. Він відповідає всім умовам.

Потрібно знайти топ-20 виконавців, у яких є щонайменше 3 треки, а мінімальна популярність усіх їхніх треків становить 60 або більше.

Для цього використав Aggregation Pipeline:

- `$unwind` — для розгортання масиву виконавців;
- `$group` — для підрахунку кількості треків, мінімальної та середньої популярності;
- `$match` — для фільтрації виконавців;
- `$project` і `$round` — для формування результату;
- `$sort` і `$limit` — для отримання топ-20.

### 3.3. Завдання 3. Нетипові треки

У цьому завданні я шукав треки, темп яких значно вищий за середній темп їхнього жанру.

Спочатку за допомогою `$group`, `$avg` та `$stdDevPop` розрахував середній темп і стандартне відхилення для кожного жанру.

Потім визначив поріг за формулою:

- Виконавець: Kina Grannis
- Темп треку: 181.74 BPM

Оскільки `181.74 > 178.5`, цей трек потрапив до списку нетипових.

## 4. Частина 3. Індекси та оптимізація

У цій частині я створив складені індекси та перевірив їхню роботу за допомогою `explain("executionStats")`.

Код знаходиться у файлі `queries/part3_indexes.js`.

### 4.1. Завдання 1. Аналіз запиту та індексація

Для аналізу використав запит:

```javascript
db.tracks.find({
  track_genre: "pop",
  "audio_features.danceability": { $gte: 0.7 }
}).sort({ popularity: -1 });
```

Спочатку перевірив його виконання без індексу. Після цього створив складений індекс:

```javascript
db.tracks.createIndex(
  {
    track_genre: 1,
    "audio_features.danceability": 1,
    popularity: -1
  },
  {
    name: "idx_genre_danceability_popularity"
  }
);
```

#### Що змінилося в плані виконання?

| Показник | Без індексу | З індексом |
|---|---:|---:|
| `nReturned` | 354 | 354 |
| `executionTimeMillis` | 83 мс | 1 мс |
| `totalDocsExamined` | 113 999 | 354 |
| `totalKeysExamined` | 0 | 354 |
| План сканування | `COLLSCAN` | `IXSCAN` |
| Сортування | `SORT` | `SORT` |

До створення індексу MongoDB використовувала `COLLSCAN` і перевіряла всі 113 999 документів, щоб знайти 354 треки.

Після створення індексу кількість перевірених документів зменшилася до 354, а час виконання в цьому тесті скоротився з 83 до 1 мс.

При цьому окрема стадія `SORT` залишилася, оскільки індекс не забезпечує потрібний порядок сортування для всього діапазону `danceability`.

#### Як зрозуміти, що індекс використовується?

У результаті `explain()` з'явилася стадія `IXSCAN`, а в полі `indexName` вказана назва створеного індексу:

```text
idx_genre_danceability_popularity
```

Також значення `totalKeysExamined` змінилося з 0 до 354, а `totalDocsExamined` зменшилося до 354.

Додатково я перевірив запит без `.hint()`. MongoDB самостійно вибрала цей індекс.

### 4.2. Завдання 2. Індекс для інших полів

У цьому завданні я створив складений індекс для пошуку музики за полями `explicit`, `audio_features.instrumentalness` та `audio_features.speechiness`.

```javascript
db.tracks.createIndex(

    explicit: 1,
    "audio_features.instrumentalness": 1,

Для перевірки використав запит:

db.tracks.find({

```

#### Порівняння результатів

Для аналізу використав `explain("executionStats")`. Щоб перевірити виконання без індексу, застосував `.hint({ $natural: 1 })`.

| Показник | Без індексу | З індексом |
|---|---:|---:|
| `nReturned` | 16 141 | 16 141 |
| `executionTimeMillis` | 153 мс | 78 мс |
| `totalDocsExamined` | 113 999 | 16 141 |
| `totalKeysExamined` | 0 | 16 602 |
| План виконання | `COLLSCAN` | `IXSCAN` |

#### Що змінилося після створення індексу?

Без індексу MongoDB перевіряла всі 113 999 документів колекції.

Після створення індексу кількість перевірених документів зменшилася до 16 141, а час виконання в цьому тесті скоротився зі 153 до 78 мс.

#### Як перевірити використання індексу?

У плані виконання з'явилася стадія `IXSCAN`, а в полі `indexName` вказано:

```text

```

Також у `indexBounds` видно умови пошуку:

- `explicit`: `[false, false]`
- `instrumentalness`: `(0.5, Infinity]`

Запит виконувався без примусового `.hint()` для індексу, тому MongoDB вибрала його самостійно.

### 4.3. Завдання 3. Покривний запит (Covered Query)

#### Чи є початковий запит покривним?

Дано запит:

```javascript
db.tracks.find({
  track_genre: "pop",
  popularity: { $gte: 70 }
});
```

**Ні, початковий запит не є покривним**, хоча поля `track_genre` та `popularity` присутні у складеному індексі.

Причина в тому, що метод `find()` без проєкції повертає весь документ, включаючи назву треку, виконавців та інші поля, яких немає в індексі. Тому MongoDB потрібно додатково звертатися до документів колекції.

Для перевірки використав `explain("executionStats")`.

**Результати початкового запиту:**

- `nReturned`: 317
- `totalDocsExamined`: 317
- `totalKeysExamined`: 620
- План виконання: `IXSCAN` + `FETCH`

Після цього додав проєкцію, щоб повертати тільки поля, які є в індексі:

```javascript
db.tracks.find(
  {
    track_genre: "pop",
    popularity: { $gte: 70 }
  },
  {
    _id: 0,
    track_genre: 1,
    popularity: 1
  }
);
```

#### Результати після додавання проєкції

| Показник | Без проєкції | З проєкцією |
|---|---:|---:|
| `nReturned` | 317 | 317 |
| `totalDocsExamined` | 317 | 0 |
| `totalKeysExamined` | 620 | 620 |
| `IXSCAN` | Так | Так |
| `FETCH` | Так | Ні |
| `PROJECTION_COVERED` | Ні | Так |
| Покривний запит | Ні | Так |

Після додавання проєкції запит став покривним.

Це підтверджується тим, що MongoDB не прочитала жодного документа з колекції (`totalDocsExamined: 0`), а в плані виконання з'явилася стадія `PROJECTION_COVERED` замість `FETCH`.

Таким чином, для покривного запиту недостатньо мати індекс тільки за полями фільтрації. Потрібно також, щоб усі поля, які повертаються запитом, були доступні в індексі.

Для цієї перевірки використовував `.hint()`, щоб дослідити покриття конкретним індексом `idx_genre_danceability_popularity`.
